# Project instructions

## Research priorities and proportionate execution

- Every experiment must answer a specific model question with the minimum informative comparison. Every engineering task must enable that experiment or repair a demonstrated failure. Every blocking gate must state the decision or scientific validity it protects. Passing tests, reproducibility or a more complete receipt graph alone do not justify additional work.
- At the current model-improvement stage, prioritize **physical field accuracy/retention, held-out State/Scale/Shape improvement, and training cost**. Report fieldwise errors and coherence tradeoffs separately; training loss alone does not establish improvement. Inference latency, deployment throughput and deployment-memory benchmarks are outside the default scope unless the user explicitly requests a deployment study. They must not become prerequisites for model scoring, checkpoint comparison or scientific conclusions.
- Apply these defaults to new plans. Preserve ongoing jobs, frozen protocols, historical evidence and existing authorization; do not silently rewrite an active campaign to satisfy a new default. Advance independent ready experiments without unrelated-source manifests, bookkeeping completion or optional diagnostics becoming launch dependencies.

## Training horizons and useful checkpoints

- Separate execution qualification from learning evidence. A smoke/resume trial establishes execution, not efficacy. For a similar pretrained-model repair study, start planning with a **100-reporting-epoch learning review and a provisional 500-reporting-epoch comparison endpoint**. Use prior learning curves and the actual model question to justify a different horizon; this is not a universal convergence claim or a default for training a source model from scratch. Add an intermediate review only when it can change a continuation decision.
- **Use epochs for every training schedule and user-facing description.** Define training horizons, learning-rate warmup/changes, checkpointing, evaluation, plotting and continuation in reporting epochs, including explicit epoch-valued configuration fields. Derive backend counters from the resolved epoch definition; never inherit an independent counter-based schedule without converting and checking its epoch duration. Preserve historical configurations/logs and resume counters. Record actual objective-bearing condition visits and dataset-pass equivalents in machine evidence for exposure comparisons, without using them as alternative training-horizon units. Increased batch exposure does not establish optimization equivalence to an older run. Keep the optimizer and coherence batch caps consistent.
- Before launch, state an initial horizon, maximum authorized horizon, complete cost forecast and continuation/stop rule. Continue within that authorization when field retention and meaningful coherence trends leave a useful unresolved question; close a persistent invalid or uncompetitive route after adequate learning evidence. Neither a weak short trial nor a round-number epoch target is sufficient reason to abandon or extend a method. Do not automatically train to 1000 epochs; an extension must have a concrete question, evidence and remaining budget. Compare matched learning ages/exposure or disclose differences.
- Measure training seconds per completed epoch and occupied GPU time from existing trainer records, with data waits/update work and assessment overhead distinguished. Reuse valid source/resume/recording qualifications; repeat only checks affected by an actual change or failure.

## Evaluation scope and turnaround

- The approximately 10% matched-sample rule below applies to each split that the question actually needs; it does not require evaluating TRAIN, VALIDATION and TEST together. Default routine held-out comparisons to the declared VALIDATION panel; add a TRAIN model-evaluation panel only for a specific fitting/diagnostic need. Keep TEST locked unless explicitly authorized. Declare selection use of VALIDATION and do not call it independent confirmation.
- Save recovery checkpoints as needed, but default expensive population assessments to a cached baseline, one useful learning review and the planned endpoint. Saving a checkpoint or refreshing ten-epoch loss curves does not authorize another inference/metric pass. Evaluate one predeclared raw or TRAIN-nominated output per checkpoint; amplitude/frontier sweeps require an explicit model question and budget.
- Generate predictions once per checkpoint, matched panel and required member manifest; reuse those saved outputs for field errors, coherence, task metrics and figures. Cache immutable SOURCE/reference transforms. Form any authorized output blends from cached endpoints rather than rerunning either model. Preserve declared physical masks, units, support, member independence/count and metric definitions; faster scoring must not silently change the scientific observable.
- Forecast the **whole evaluation path**, including input/output, GPU generation, CPU State/Scale/Shape scoring and the final CPU queue tail. Normally target evaluation's added wall time at no more than **20% of the planned training wall time**; report CPU/GPU work separately. This is a planning target, not a new adoption gate or permission to shrink the required 10% coverage. If it does not fit, first remove unnecessary checkpoints, output policies and metrics, reuse exact computations, and use bounded existing CPU concurrency. If essential scoring still exceeds the target, budget that explicitly before launch rather than discovering the tail after training.
- Return field-retention and available coherence results from saved predictions without waiting for unrelated profiling or accounting. State which required metrics remain pending before making a final decision. Use existing scoring tools and a bounded worker count suited to measured CPU/memory cost; do not build a new scheduler, provenance framework or broad synthetic-test programme to accelerate one comparison.
- Keep job-level costs and failed attempts honest. Unknown costs remain unknown or explicitly bounded; only affected cost claims become unavailable. Do not make subsecond bookkeeping reconstruction or exhaustive administrative attribution a prerequisite for otherwise valid model measurements. Retain required final-report checks, without report-ready presentation work for every preparatory diagnostic.

## GPU portability

- Keep GPU selection in runtime configuration, separate from frozen scientific protocols and code provenance. Do not hard-code physical GPU indices or UUID allowlists in training/evaluation code, frozen contracts or qualification gates.
- Record the actual device and environment, check compatibility and ownership, and honor the latest explicit device exclusions. A permitted device change alone requires no scientific re-freeze, requalification or extra approval. Superseded device preferences must not survive as immutable restrictions.
- For hardware performance comparisons, measure the compared methods on the same device or label hardware differences; do not freeze a particular device UUID.

## Default model-evaluation coverage

For all future model evaluations, including TRAIN, VALIDATION, TEST and diagnostic metric evaluations, use approximately 10% of dataset samples by default, selected either by reproducible random sampling or the first 10% in dataset order. Use matched sample IDs across compared models. Full-population evaluation requires my explicit request. Words such as ‘complete’, ‘matched comparison’ or ‘final report’ do not independently authorize full-population evaluation.

## Loss-curve recording and refresh

- **Loss-curve refresh cadence.** Save the first loss curves as soon as history is available, then refresh them every **10 completed epochs** during all training stages, including resumed training, and additionally at validation checkpoints, pauses and completion. Per-experiment plans, launchers and generated configurations must retain this cadence; do not increase the interval or tie it to validation/checkpoint frequency unless the user explicitly requests it. The legacy `runtime.plot_every_steps` key is interpreted as an epoch interval and must default to `10`. Refresh curves from already recorded histories without adding inference, evaluation or optimizer updates. Keep complete histories and curve files in the case-owned run `logs/` directory. Automatic trainer plotting does not authorize conversational polling or extra monitoring.

## Mandatory run-monitoring policy

These rules apply throughout this repository, including all cases, experiments, training runs and delegated tasks. They apply to every primary or coordinating agent.

1. **The primary agent must never repeatedly poll an ongoing run unless the user explicitly requests primary-agent polling.** This includes repeated reads of status files, logs, terminal/tmux output, process or GPU state, training sessions and checkpoint directories solely to learn progress. A request to finish an experiment, wait for completion, monitor a run or report its status does not authorize repeated primary-agent polling. A direct status question permits one bounded status check.
2. **All ongoing-run monitoring must be delegated to a Luna light subagent:** use `model: "gpt-6-luna"` and `reasoning_effort: "low"`. Give it the run identity, expected duration or available epoch-time estimate, meaningful milestones, completion/failure signals and notification requirements. Do not substitute the primary agent or another model if Luna is unavailable; report that monitoring cannot be delegated. Do not inspect an existing run merely to prepare a monitor when its launch receipt or available timing evidence already suffices.
3. **Schedule sparse checks before monitoring begins.** Estimate the expected completion time and, only when useful, a few intermediate checkpoints that support an actual decision. The monitor must wait until those times rather than use a short-interval polling loop. Per-epoch or per-update progress probes are prohibited by default. If timing changes, revise the next check from the latest scheduled observation instead of repeatedly checking whether the estimate was correct.
4. **Use push notifications.** The Luna subagent notifies the primary agent at the agreed milestones, completion or an actionable failure. Include the run identity, observed state and relevant artifact paths; omit unchanged "still running" messages and raw log dumps. The primary agent must not repeatedly query the monitor, list agent status, send follow-up status requests or loop on wait timeouts to recover the same progress information.
5. **Keep the primary agent productive.** While the monitor waits, do independent useful work or hand off/end the turn with the monitoring arrangement recorded. Do not keep the primary agent in a sleep/check or wait/check loop solely because training is running.
6. **Preserve scientific recording.** Automatic trainer logging, validation, checkpointing and loss-curve updates continue at their required cadence. Their cadence is not a conversational polling schedule. Necessary one-time launch/resume verification, a bounded diagnosis after a failure notification, and final artifact analysis after completion are permitted; none may become recurring primary-agent monitoring.
7. **Monitoring is read-only unless separately authorized.** This policy does not authorize stopping, restarting or modifying a run, changing its configuration, or altering checkpoints. Ending a monitoring task does not mean ending the experiment.

When preparing an execution plan or prompt that includes a long-running job, link to this policy and name the Luna monitor and intended check schedule. An explicit user instruction can override the corresponding monitoring restriction; routine execution instructions cannot.
